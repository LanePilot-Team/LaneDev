# Android 用戶端驗證與待確認事項

## 2026-11-07（續二）：起終點依來源吸附、兩處資料修正

延續下一節「Google 對照」的三類原因，依使用者決定修正。

### 一、起終點吸附依來源區分（`graph.ts` `snapCandidates`／多起多終 A*）

- 設計衝突：原設計（測試 #47 等保護）是「地圖上點在哪一側車道，就從／到那一側」，車道級地圖的點選位置有意義；Google 則不管點在哪側都挑最順的方向。使用者決定**依來源區分**：
  - **地圖上點車道**（停靠點只有座標）→ `'lane'`：完全維持原邏輯（起點取最近行向；終點先試點選那一側，無分隔雙向路走不通才退另一側；有分隔只取點選側）。
  - **搜尋地點／地址／目前位置**（停靠點帶 `placeId` 或 `label`）→ `'area'`：
    - 起點：附近（最近路段＋40 m 內）每條路、每個可行行向都是候選，含分開建模的對向單行車道（高楠公路北上側在南下側外 10～27 m）。
    - 終點：最近那條路照原規則；另納入 15 m 內的其他道路（修正點在巷口卻吸到巷子），與最近候選反向平行（>150°）者視為對向車道不列入——**不改成可以停在分隔道路對面**，仍待組內決定。
- 每個候選帶「離點選位置的距離 × 0.7 s/m」懲罰，A* 改為多起點 × 多終點一次搜尋，挑「行駛＋車道難度＋距離懲罰」最低者。只有一組起訖時與原本完全相同。
- 判定來源：`placeRoute.ts stopSnapMode()`；規劃（`usePlanner`）與偏航重規劃各段（`useDrive`）都依停靠點來源傳入。偏航重規劃第一段有 GPS 方位時仍依方位（不受影響）；沒有方位時當成目前位置（`'area'`）。
- 效能（PC、30 組隨機）：汽車 lane 190 ms／area 185 ms，機車 237／241 ms，無差異。

### 二、資料修正（`fixups.ts applyPostJournalFixups`，套在人工 journal 之後，不動官方資料檔）

依據是 Google 比對，**尚未現場確認**；標註／OSM 修正後應移除這兩項。

- **高楠公路南下機車道箭頭**：`294647549`、`294647550`、`564743848`（各 1 車道）人工標註「只能直行」→ 覆寫為「直行;右轉」。原本擋掉 1003巷、水管路等 7 個右轉出口；機車道往南又直接開出地圖（OSM 2026-01-07 切出的延續段 `1465030882` 不在 shard 內，補上也只是把斷頭往南移 700 m），所以從這裡出發的機車找不到任何路。修正後高楠 → 加昌機車 **2.10 km，與 Google 2.1 km 路徑相同**（1003巷 → 環廠道路 → 學專路 → 高峰街）。
- **旗楠公路（台22）開放汽車**：`25724899`、`256795148`、`884583094` 移除 `motorcar=no`。楠梓新路 → 高楠汽車 1.91 → **1.30 km（= Google）**。

## 2026-11-07（續）：匝道分流被直行箭頭封死、直行假換道、高楠公路南下機車道斷頭

延續同日與 Google 地圖的比對。診斷方法同上一節：同一組起訖分別跑「有車道規則」與「不套車道規則」的 A*，再沿後者逐一重算車道決策（帶車道狀態），找出被拒絕或被加重成本的轉移。

### 一、匝道分流被直行箭頭封死（汽車，已修正）

- 案例：加昌路191號 → 高楠公路南下（中油加油站南方）。汽車 **2.72 km**：加昌路 → 後勁橋 → 往北鑽高楠公路1616巷／1742巷（service）→ 左轉高楠公路南下。不套車道規則為 **1.52 km**：楠陽高架橋往東 → 下橋匝道 `103678985` → 高楠公路南下。
- 唯一被拒絕的轉移：楠陽高架橋往東（`103678964` B 向）→ 匝道 `103678985`，在 node `1196964677`（120.3225, 22.7220），`explicitly-incompatible`。
- 該方向箭頭 `through|through|through` 來源是 **`lanepilot-segment`**（LanePilot 標註）；OSM 原始為兩條單行橋面、無 turn:lanes，couplet 合併後套上此標註。分流角 33° 被歸為 `slight-right`，而且兩條路名不同、不算同路微彎，所以要求「有右轉箭頭的車道」——三條都只標直行 → 沒有車道能下匝道。
- 修正（`graph.ts laneTransitionPlan`）：主線以 `slight-left/right` 分流進 `*_link`、且照箭頭會被拒絕時，退回推論模式重判（右分流走最外側、左分流走最內側）。箭頭本來就允許的分流照舊；一般道路同角度轉入仍受箭頭限制（有測試）。
- 標註端建議：匝道分流處的最外側車道可標 `through;slight_right`，讓資料本身就正確。

### 二、直行時被算假換道，機車被推進巷弄（已修正）

- 案例：楠陽路 → 後勁國中（機車）。起終點都選對邊時，有規則 2.06 km 走加昌路18巷 → 1747巷87弄 → 惠豐橋 → 金和街；不套規則 1.98 km 走加昌路 → 後勁橋。後者沒有任何轉移被拒絕，是被成本推開的。
- 根因：`laneDecision.ts candidateOrder()` 把「專用車道」排在「留在目前車道」之前，直行也一樣。機車每過一個路口，`graph.ts` 都把它設回最外側車道，而最外側常是 `through;right` 共用道 → 程式要求「換到專用直行道」，每段路都算一次假換道（2 s＋準備距離不足）。加昌路上累積約 20 s，大於鑽巷子多花的 18 s。
- 這是系統性的：凡是最外側車道為直行兼右轉的大路，機車都被多算成本。
- 修正：直行時先比「離目前車道多遠」，再比是否專用（轉彎仍維持專用優先，原註解的用意不變）。

### 三、高楠公路南下機車道斷頭（資料問題，未修，需組員處理）

- 現象：從高楠公路南下側出發的機車，三個版本都對任何目的地回 `lane-direction`。
- 起點只能吸附到高楠公路南下機車道（`294647549` → `294647550` → `564743848`，人工標註 1 道、只標直行；主線南下 `motorcycle=no`）。沿途右轉出口都被直行箭頭擋掉，而機車道最南端 node `5456271579`（120.32331, 22.70138）**沒有接任何路**。
- OSM 歷史：2026-01-07 `564743848` 被切成兩段（v19，38→23 個節點），後半段成為新 way **`1465030882`（高楠公路，motorcycle=yes）**；該節點另接 **八德二路 `566619281`**。這兩條在 `road_database.json` 與三個 LanePilot shard（`area_4212533`／`4212599`／`4212683`）裡**都不存在**。
- 需要：資料管線把這兩條補進來（或檢查跨行政區邊界、近期才切分的 way 是否被漏收）。程式端無法補出不存在的路。
- 這也代表其他「末端沒接任何路」的斷頭值得全面掃一次（建議下一步）。

### 四、起終點吸附到對向車道（未修，待討論）

- 楠陽路、加昌路都有中央分隔。地圖點選的起點沒有行進方向，程式取最近的一側；選到往東那側時，先往東 164 m、鑽 30 m service 巷迴轉再往西（約 +0.45 km）。終點則要求一定要從吸附的那一側抵達，後勁國中吸到加昌路南側時，要繞加昌路127巷 → 12弄 → 179巷兜回來（約 +0.16 km）。Google 的做法是停在對面就算到。
- 可能修法：規劃時點選的起點兩側都試、取成本低者（GPS 導航有方位，維持現狀）；終點允許對側抵達或給小懲罰——後者涉及「要不要叫人過馬路」的產品決定，需組內討論。

## 2026-11-07：機車專用道被車道規則封死（機車路線大繞路）

起因：與 Google 地圖比對同一組起訖（加昌路191號 → 楠梓車站）。汽車兩邊一致（加昌路 → 楠陽高架橋 → 楠陽路 → 朝新路 → 楠梓新路）；機車 Google 1.5 km／4 分，我們 **3.71 km**，往南繞進中油「環廠道路」再走高楠公路上來。

### 根因

- 楠陽高架橋本體與引道 `motorcycle=no`（正確，機車本來就不能上橋）。Google 給機車的是旁邊獨立的「機車專用道」系列 way（`24205221`、`24451058`、`293380616`、`912306403`、`256795147`…），我們的路網裡也有、且連通。
- 這些 way 原始 OSM 只有 `motorcar=no`、`motorcycle=yes`、**沒有 `lanes`**，進路網後被建模成「汽車車道 0、機車道 ≥1」的純機車道路體（`lanesForward=0`、`motoF=true`、`motoCountF≥1`）。渲染與 `laneOffsets` 都正確處理了 0 汽車車道。
- 但路口車道決策 `graph.ts laneTransitionPlan()`／`approachSealed()` 把 `guidanceForRoadDirection().laneCount`（**只算汽車車道**）直接交給 `resolveLaneDecision()`，而 `laneDecision.ts` 遇到 `laneCount === 0` 一律回 `explicitly-incompatible`。
- 結果：機車**開得進**純機車道，**出不去**（從它出發的每個轉移都被拒絕），整套機車專用道對 A* 等於死路。關掉車道規則重跑同一組起訖，機車即得 1.49 km／128 s、路徑同 Google——證實是這條規則，不是成本權重。
- 影響範圍：全路網 88 條 way、約 10.8 km（清豐路 16 段、土庫一路、機車專用道系列、惠民機車地下道、慈雲寺旁機車地下道…）。凡需經過純機車道的機車路線都會被逼繞路。
- 繞路之所以選「環廠道路」：它是 `highway=service`、無 `access` tag，用 service 預設 40 km/h 計（比 residential 30 還快）。這是 2026-10-29 已記錄但未修的「service 速度／access」問題，不是本次主因；主因修掉後此案例不再經過它。

### 修正（`graph.ts` 新增 `decisionGuidance()`）

- 只改車道決策的**輸入**：機車在「汽車車道 0 且機車道 ≥1」的方向，視為 1 條無箭頭的推論車道（可直行／轉彎）。`laneDecision.ts` 本身不動——汽車遇到 0 車道照舊拒絕（這些路段 `motorcar=no`，汽車本來就進不來）。
- 下游 `laneIndexOffset()`／`laneChoiceAreas()` 都以 `max(1, laneCount)` 換算並夾在機車可用範圍內，車道索引 0 會落在機車道上，HUD／路線帶不需改。HUD 顯示用的 `span.laneGuidance` 仍是原本的汽車車道導引，未改。
- 測試：`graphLaneDecision.test.mjs` 新增 2 項（純機車道可轉出；0 車道且無機車道仍不可通行）。新測試在修正前的 `graph.ts` 上確認會失敗。

### 驗證

- `npm test` 283 項全過；`tools/build-runtime.mjs` 24 組路線還原一致（24 組可通行）。
- 用正式預計算路網、新舊兩版 `graph.ts` 對拍：
  - 截圖案例：機車 3.71 km／328 s → **1.49 km／128 s**（加昌路 → 機車專用道 → 楠梓新路，與 Google 同）；汽車 2.16 km、1.99 km 兩案完全不變。
  - 隨機 200 組起訖（固定種子）：**汽車 200 組全部相同**；機車 156 組相同、38 組改變（合計縮短 28.75 km，例：7.74→5.04、14.18→11.62、5.27→3.07 km）、6 組原本找不到路→可達、0 組原可達→失敗。另有 2 組顯示時間略增（A* 成本含車道難度、顯示 ETA 不含，兩者不必同步；未逐一檢查）。

## 2026-10-29：路線演算法分析與準備距離懲罰修正

用正式 `graph.ts` 與預計算路網跑 5 組起訖 × 汽機車並做消融比對，發現以下問題。第一項已依使用者要求修正，其餘仍待決定：

## 2026-09-17：搜尋規劃整合、定位朝向、語音與啟動診斷

- 主畫面只保留搜尋入口與定位／設定，移除舊右側工具列。搜尋目的地後按「路線」，起點預設目前位置。
- 起點、終點及新增停靠點均可直接打字搜尋，沿用同一組搜尋結果與地址顯示；更換任一端點只更新該端點並重新規劃，切換汽／機車重新計算。
- 移除「使用目前位置作起點」「自訂起終點」模式按鈕；「目前位置」保留在起點搜尋的建議選項，供自訂後恢復 GPS 使用。
- 定位標記改為藍點＋朝向扇形（隨地圖旋轉對齊）；無可靠／新鮮朝向時不顯示扇形。
- 地址不再回退為「休閒」等分類。來源有地址則完整顯示；缺漏時查詢 Android Geocoder，標示「附近地址（非確認門牌）」。離線、無 Geocoder 或查無資料時顯示地址缺漏及座標，不能保證每筆 POI 都有正式門牌，也不捏造地址。查詢由系統地理編碼服務處理地點座標，不另傳手機實際位置。
- 原 TTS 選聲音前未初始化語言、排除尚未下載聲音、返回設定時未強制重新載入；現改先 setLanguage，選中文聲音、提供真正的引擎資料下載入口，回到 App 重新初始化。首次引擎連線失敗可在播報時重試。
- 語音指定 navigation/speech 音訊用途、媒體音量控制；試聽不受導航靜音開關影響，顯示播放回呼與媒體音量，避免「開過設定就等於有語音」的假設。
