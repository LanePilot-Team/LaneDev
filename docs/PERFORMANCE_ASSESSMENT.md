# 啟動與導航流暢度：實作與評估（2026-09-26）

使用者確認後，第 3、4 項已實作於原工作區與分支；以下先記錄本輪結果，再保留原始評估。

## 本輪實作

- `buildRuntime.ts` 承接原初始化的唯讀演算法，於 `npm run build` 前生成固定道路、待轉區、路面、標線、路名、建築與高架高度。手機不再執行道路前處理、待轉區生成或第二份繪圖路網建立。
- `RoadGraph.snapshot/fromSnapshot` 以索引保存道路、反向邊與節點關係；Lane Base 的 Map／Set 由版本化 codec 還原。導航與繪圖資料分檔，MapLibre worker 讀取繪圖來源。
- 繪圖輸出移除樣式及道路資訊卡不使用的屬性；以 1e-10 度（約 0.01 mm）容差去除共線冗餘點。特徵數、孔洞、必要屬性保留；不簡化導航道路幾何或更改通行限制。dividers 檔案由約 120.5 MiB 降至 12.3 MiB。
- 檔案採內容雜湊命名；建置檢查來源／演算法版本與檔案 SHA-256，Android 匯入再次校驗。執行時驗證導航資料雜湊。損毀／缺檔顯示錯誤及重試，30 秒逾時保留錯誤提示，不無限 loading 或退回大量計算。
- 移除外部 glyph URL，沿用安裝版本 MapLibre 支援的本機字形繪製。離線不必等外部字型服務。
- `GpsAnimation` 依已量測的路線帶里程插值；車輛和鏡頭使用同一畫面位置。每幀用二分搜尋找路線段，不按速度積分、不跨轉角走捷徑，也不預測未收到的位置。
- 平滑過渡最長約一秒，會帶來小幅顯示延遲；導航提示、抵達與偏航仍用真實定位判斷。重複／過期定位不推進；弱訊號、背景、定位錯誤與重新規劃會停止／重設動畫，沒有新定位就停止在最後量測位置。
- 建築使用網格索引查詢附近範圍，變更時用 `updateData` 只移動受影響 feature；待轉區高亮用 feature-state，不重建全部標線。手動拖圖後鏡頭不跟隨，但車輛仍可動。

## 本輪驗證與界線

- 46 項前端測試通過，包含跨北方角度、轉角路徑、不同幀頻一致性、停止／重設、建築差量及繪圖精簡。TypeScript、Vite、Android assembleDebug、testDebugUnitTest 通過。
- 每次預計算均驗證完整圖快照、Lane Base／待轉區／左轉道序列化，以及 24 組汽機車路線結果（22 組成功、2 組無路線）完全一致；高架各段五個位置的高度還原一致。共 11,036 條導航道路、343 個待轉區，官方原始資料未改。
- Pixel 6／API 37 模擬器、4 GB RAM、軟體 GPU。比較指標為 WebView 文件開始至初始化完成，不含文件之前的 Android Activity 啟動；不是使用者真實手機 benchmark。
- 同輪舊 APK 冷啟動約 26.251 秒；新版第一輪約 6.862 秒。最終 APK 在 Wi-Fi／行動資料關閉時約 6.529 秒（地圖來源亦已載入），網路已還原；不是只提早拿掉 loading。
- 最終 APK：每秒一筆注入定位，四次移動更新產生 155 個不同的中間畫面位置。觀測畫面更新間隔 p50 約 23.4 ms、p95 約 46.2 ms；這是軟體 GPU 的測試軌跡，不是保證 60 FPS 的 GPU benchmark。
- 定位停止後沒有持續動畫；拖開地圖後鏡頭保持不動，車輛另更新 34 幀。測試軌跡沒有對 roads／roadSurfaces／dividers／buildings／occludedBuildings 呼叫整份 setData。
- 另在實際 MapLibre 驗證建築差量移入／還原、1,164 個建築數目保留；待轉區 feature-state 開關通過，外部字型請求為零。
- Debug WebView 注入兩種故障：導航 JSON 校驗失敗、dividers 圖層缺檔。兩者均顯示明確錯誤及「重新載入」、保持導航停用；移除故障注入後重新載入成功。未改寫 APK 資料檔。
- 搜尋、更換起终點、恢復目前起點、汽機車切換及導航語音回歸通過。真實行駛、各廠牌 GPS、長時間耗電／熱節流及低階手機幀率仍待實機測試。
- 預計算會增加 APK 容量（本輪 debug APK 約 31 MiB），換取手機啟動時不重複運算。一般 Android Studio 建置仍只使用已提交的 assets，不要求使用者有 Node.js。

## 原始評估（以下描述修改前的狀態）

## 3. 啟動等待：可改善，建議在打包前預先計算

目前 APK 已有原始道路資料庫，但它不是可直接使用的導航／繪圖成品。`web-source/src/core/staticDatabase.ts` 的快取只存在程序記憶體，每次冷啟動仍需解析與前處理。`web-source/src/app/mapCore.ts` 的初始化會整理道路幾何、生成路面、建立導航圖、產生待轉區，再建立繪圖路網及標線。

既有 2026-09-17 模擬器分段紀錄合計約 34.3 秒，其中待轉區 11.13 秒、道路幾何 7.91 秒、路面生成／送入來源 5.21 秒、標線等 2.65 秒，導航圖本身僅 0.45 秒。另一次約 24.2 秒。這些是歷史量測，不是本次已改善的成果，也未在使用者手機重現一分鐘等待。

### 建議實作

1. 將固定道路幾何、官方待轉區、標線與路面繪圖資料，以及導航圖節點／鄰接關係在建置期產生，連同 APK 發布。第一次啟動也不必先等完整計算；比安裝後首次才運算更合適。
2. 執行時讀取已產生的資料；保留官方資料唯讀及汽機車通行限制。圖結構含 Map 等執行期物件，必須設計序列化與還原格式，不能直接對整個類別 JSON.stringify。
3. 使用來源雜湊、格式與演算法版本驗證成品。資料更新時重新生成；若另設裝置快取，需驗證完整性與原子替換。不能無聲地退回一分鐘計算。
4. 起終點確定後的路線搜尋及偏航重規劃仍按需執行；預計算靜態路網不等於預算所有路線。
5. 測量剩餘的 JSON 解析、MapLibre 資料處理及 GPU 上傳，再決定是否分區載入、延後非必要建築或使用 Worker。Worker 能減少主執行緒阻塞，但不會讓計算成本消失。

僅將原始 JSON 搬進 SQLite 不會消除上述生成成本。也不能只提前隱藏 loading，讓道路限制尚未準備完成就開始導航。

### 其他需確認的啟動因素

- 地圖字型使用外部服務，需測試離線／弱網的等待；尚無證據認定它是一分鐘等待的主因。
- 初始化非同步路徑缺少涵蓋全部階段的失敗收尾，資源失敗時可能留下 loading；需補失敗情境測試後處理。
- Google 搜尋是按需載入，不應把缺少搜尋 API key 直接當成正常啟動慢的原因。

驗收須比較舊／新道路、待轉區與標線幾何、代表性汽機車路線及限制的一致性，並在實機記錄冷啟動、暖啟動、離線啟動、首次可操作及導航可用時間、尖峰記憶體。可大幅減少重複計算，但完成實機量測前不承諾固定秒數。

## 4. 畫面卡頓：可改善，位置更新與繪圖需要分開

### 已確認的程式路徑

- `gpsNav.ts` 優先使用裝置回報速度；只有缺少速度時才以距離／時間估算。這個公式本身不是畫面刷新計時器。
- 導航狀態隨 GPS fix 更新；`useDrive.ts` 在同一次更新直接設定車輛座標並呼叫鏡頭 `jumpTo`，兩筆定位之間沒有位置插值。即使地圖能高幀率繪製，仍會看見低頻定位造成的跳動。
- `models3d.ts` 重用既有車輛模型，並非每筆 GPS 都重建整張地圖。鏡頭移動需要重畫可見畫面是正常的，但不等於重新讀取整份路網。
- `occlusion.ts` 計算建築遮擋；遮擋集合改變時重新分配整批建築，對兩個 GeoJSON 來源呼叫 `setData`。不是每筆 GPS 都觸發，但可能帶來額外資料處理與卡頓。
- 3D 道路／建築、遮擋計算與 GPU 負載仍需實機剖析；目前沒有 FPS 數據可證明所有卡頓都只來自 GPS。

### 建議實作

1. 保留真實 GPS 與時間戳作為導航、偏航、抵達判斷的依據；另外建立 requestAnimationFrame 顯示迴圈，以經過時間在定位點之間平滑移動及旋轉。
2. 車輛與跟隨鏡頭使用同一份平滑位置；轉角處沿路線處理，方向跨越 359／0 度取最短旋轉。畫面更新頻率不綁在速度數字或 GPS 回報頻率上。
3. 採取小幅緩衝插值或有上限的短暫外推，必須評估延遲與準確度取捨。GPS 中斷、低可信度、停車、重規劃及切換前後景均需重設／停止，不能為了順暢持續假裝車輛前進。
4. 使用者拖動地圖時車輛仍可更新，鏡頭暫停跟隨；背景及閒置時停止不必要動畫，避免耗電。不引入模擬駕駛或播放倍率。
5. 靜態地圖來源重用；遮擋先用空間索引找附近建築，避免全量掃描與反覆提交整份資料。依 MapLibre 圖層屬性支援程度選擇 feature-state、局部來源或小型覆蓋層，不假設所有透明度屬性都能直接使用 feature-state。
6. 不以每幀 React state 更新整個面板。再用效能追蹤決定是否需要調整 3D 負載，而不是直接刪除官方資料或必要導航細節。

驗收需在真實手機記錄 GPS 頻率、動畫幀間隔與長任務、`setData` 次數／資料量，並測試低速、停車、轉彎、定位中斷、快速重規劃及手動拖圖。應區分「定位跳動」與「GPU 畫不完」；平滑位置能解決前者，不能保證所有硬體都維持 60 FPS。

## 建議順序與範圍

原提案順序：先做靜態資料預計算並驗證導航結果一致，再做真實 GPS 顯示插值與鏡頭同步，最後依實機追蹤處理建築資料更新及 GPU 瓶頸。本輪已依使用者確認實作，仍保留實機驗收界線。
