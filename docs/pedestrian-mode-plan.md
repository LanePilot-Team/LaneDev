## 1. 三個先量出來的事實（會決定整個設計）

### 1.1 路網裡完全沒有人行道 ⚠ 最重要

實測 `road_database.json` 的 5478 段，道路等級分布：

```
service 2562／residential 1793／tertiary 498／unclassified 264／primary 184
motorway 48／motorway_link 48／primary_link 29／trunk_link 18／secondary 16
trunk 12／tertiary_link 4／living_street 2
```

**沒有一段 `footway`／`path`／`pedestrian`／`steps`**，而且有 251 段明確標了 `foot=no`。

也就是說這是一份純粹的**可行車**路網。直接拿來做行人導航的後果：

- 公園步道、人行天橋、地下道、蓮池潭環湖步道、都會公園內部動線——**全部不存在**。
- 捷運站的地下連通道不存在，所以「走到對面月台」會被規劃成繞到路口過馬路。
- 沒有行人穿越道資料，過馬路只能靠「走到路口」來近似（在台灣其實還算符合現實）。

**這是要你決定的第一件事**（見 §6）：接受粗略版，還是另外抓 OSM 人行道資料。

### 1.2 不要把 `'foot'` 加進 `Profile`

`Profile = 'car' | 'moto'` 已經深入車道級邏輯：車道偏移（`laneOffsets`）、
兩段式左轉、待轉區、車道指引、路口決策。加上第三個值，等於要在幾十處
加上「如果是行人就跳過」的 guard，把車道邏輯弄髒，而且行人一項都用不到。

**行人走獨立的簡化圖**：`src/core/walkGraph.ts`——無向、不管 oneway、
不管車道、不管轉向限制，只有節點與邊長，加上排除規則（motorway／`foot=no`）。
它跟 `RoadGraph` 共用同一批道路幾何，但不共用那套車道語意。

### 1.3 完整的時刻表路由（RAPTOR）不做

多模式時刻表路由是一個獨立的研究題目，做完會吃掉整個專案的時間。
改用**「轉乘建議」**：用我們已經有的**站序資料**找出連通的路線，
時刻表只拿來估時間與班距，不拿來做路徑搜尋。

這對使用者其實更誠實——你自己講的「公車班次較難確認」，
所以正確的產品行為是**同時給幾條路徑＋各自的不確定性**，而不是假裝算得出精確到站時間。

## 2. 產品長什麼樣

工具列多一個模式：**🚶 行人**（與瀏覽／編輯／規劃路線並列）。
選起點與終點後，右側面板列出**多條方案**，每條長這樣：

```
┌────────────────────────────────────────┐
│ 🚶 全程步行            32 分 · 2.4 km   │
│    最準，不受班次影響                     │
├────────────────────────────────────────┤
│ 🚲 YouBike             14 分 · 3.1 km   │
│    走 3 分到「捷運後勁站」(可借 12 台)      │
│    騎 9 分 → 「楠梓加工區」(可還 8 位)      │
│    走 2 分到終點                         │
├────────────────────────────────────────┤
│ 🚌 公車 紅58            21 分 ± 班距      │
│    走 4 分到「德民路口」                   │
│    搭 6 站 → 「楠梓火車站」                │
│    約 15 分一班 · 末班 22:30              │
├────────────────────────────────────────┤
│ 🚇 捷運 R 紅線          18 分            │
│    走 6 分到「後勁站」                     │
│    搭 2 站 → 「都會公園站」                 │
│    約 6 分一班                           │
└────────────────────────────────────────┘
```

點一條就把該路線畫在地圖上（各段用不同顏色：走路虛線、公車橘、捷運紅、單車綠）。

**不做假精確**：公車那條標「± 班距」而不是給一個像是算過的到站時間。

## 3. 路徑產生邏輯

每一種都是獨立的簡單演算法，不是一個大的多模式搜尋。

| 方案 | 做法 | 需要的資料 |
|---|---|---|
| 全程步行 | walkGraph 上跑 A*（步速 4.8 km/h） | 現有路網 |
| YouBike | 起點附近最近的 N 個站 × 終點附近最近的 N 個站，各組合算「走＋騎＋走」總時間取最佳（騎速 13 km/h） | 站點（已有）＋即時車位（見 §5） |
| 公車 | 起點步行圈內的站牌 ∩ 終點步行圈內的站牌，找**同一條路線且站序方向正確**的配對 | 站序（已有）＋班表（要補） |
| 捷運／輕軌 | 同公車，改用車站序列 | 車站（已有）＋站序與時刻表（要補） |

三段式（走路→公車→轉捷運→走路）**不做**——組合爆炸，而且兩區範圍內用不到。

## 5. YouBike 即時車位：這一項推翻了先前的決定

你之前核定「全案不含任何即時資料」，但這次明確要「查詢現有腳踏車數量」。
限制沒有變（`tdx-transit-plan.md` §1.2）：**靜態站台沒有後端可以藏 client_secret**。

三個選項：

| | 線上版（GitHub Pages） | 本機 dev | 成本 |
|---|---|---|---|
| **A. 只做本機** | 顯示「即時車位僅本機可用」，仍顯示車柱總數 | ✅ 有即時 | 最低，Vite middleware 約 40 行 |
| **B. 加 Cloudflare Worker** | ✅ 有即時 | ✅ | 多一個部署目標，約 30 行 Worker |
| **C. 不做即時** | 只顯示車柱總數 | 同左 | 零 |

**建議 A**：畢專 demo 通常在自己筆電上跑，本機有即時就夠了；
線上版明說限制也比假裝有資料誠實。之後要升級成 B 隨時可以，介面一樣。

## 6. 需要你決定的三件事

1. **人行道資料要不要抓？**（§1.1）
   - **不抓**：行人路線走車行道路。快，但公園步道、天橋、地下道都沒有，
     穿越半屏山／都會公園的路線會繞遠或走不出來。
   - **抓**（建議）：用 Overpass 抓兩區的 `footway/path/steps/crossing`，
     專案已有 Overpass 前例（`scripts/fetch_nanzi.py`、README 的備援底圖）。
     多約半天，但行人路線的品質差很多——這是行人模式的地基。

2. **YouBike 即時車位**：§5 的 A／B／C。

3. **路線種類的優先順序**：四種全做，還是先做「步行＋YouBike」再加大眾運輸？
   （步行與 YouBike 不依賴班表，可以先獨立驗收。）

## 8. 驗證方式（沿用專案慣例）

- `src/core/walkGraph.test.mjs`、`src/core/transitRoute.test.mjs`：純函式單元測試。
- `npm run audit:walk`：離線稽核——隨機抽 N 組起訖點，回報有解率、
  是否誤走高速公路／`foot=no` 路段、路線長度與直線距離的比值（繞路程度）。
- `npm run audit:transit-route`：抽樣起訖點，回報四種方案各自的產生率與合理性。
- 畫面一樣沒法截圖（MapLibre 在 Browser pane 未顯示時不 composite），
  用靜態 HTML 預覽看方案卡片。
