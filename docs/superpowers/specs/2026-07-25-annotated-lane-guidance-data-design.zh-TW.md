# 人工標註車道導航資料設計

**日期：** 2026-07-25
**狀態：** 等待使用者確認
**分支：** `codex/lane-guidance-preview`

## 問題說明

目前即使 LanePilot 已經有人工作業標註的 `lane_movements`，車道預覽仍可能顯示「車道建議（系統推測）」。

目前執行時存在三個彼此獨立的問題：

1. 系統啟動時會自動讀取內建的 `annotations.jsonl`，但只用它建立二段式左轉待轉區；車道資料只有透過「匯入地圖」功能才會套用。
2. 地圖上的路面箭頭可以依照路口幾何自動推測，因此地圖上看得到箭頭，不代表明確的車道方向資料已經傳入 HUD。
3. HUD 目前讀取車輛當下所在道路的屬性，但每個路線轉彎步驟其實已經知道真正相關的進場道路與路口。

目前預設路網包含 3,184 個路段，其中只有 11 個路段具有明確的 OSM 車道轉向標籤。與該路網相符的內建標註中，有 943 筆至少包含一個已知的車道方向。系統必須自動使用這些標註。

## 目標

- 不需要手動匯入，就能自動使用內建的 LanePilot 車道標註。
- 保留特定路口的進場標註，不把同一條 OSM 道路上不同路口的資料壓成同一份。
- 人工標註的明確值優先於 OSM。
- 如果人工標註中的某條車道是 `unknown`，而 OSM 同一條車道有明確值，則使用 OSM 補上。
- 只有人工標註與 OSM 都無法提供可用資料時，才使用系統推測。
- 精簡車道資料索引完成載入前，不允許開始導航。
- 導航期間的查詢必須輕量且同步，以利未來轉成手機 App。

## 不在本次範圍內

- 修改 `annotations.jsonl` 的資料格式或來源內容。
- 編輯或修正既有標註。
- 取代目前的地面箭頭產生系統。
- 加入網路同步或後端服務。
- 重構與本功能無關的路線規劃或地圖繪製程式。

## 資料優先順序

車道資料依照以下順序選擇：

1. 進場道路、路口節點與行駛方向皆相符的 `intersection_approach` 標註。
2. 道路與行駛方向相符的 `segment_direction` 標註。
3. 道路與行駛方向相符的舊格式道路標註。
4. 明確的 OSM `turn:lanes`、`turn:lanes:forward` 或 `turn:lanes:backward`。
5. 根據幾何與路口出口進行系統推測。

優先順序以單一車道為單位套用：

- 人工標註的已知值會取代同一條車道的 OSM 值。
- 人工標註為 `unknown`、空字串或缺少該車道時，使用同一條車道的 OSM 值。
- 如果兩個來源都不知道該車道方向，該車道維持未知，再由預覽模型決定是否需要推測。
- 人工標註的車道數有效時，以人工標註為準；否則使用道路該行駛方向的車道數。

同一條 OSM 道路上，某個路口的進場標註不得影響其他路口。

## 精簡的執行時資料

`annotations.jsonl` 繼續作為完整資料來源。建置腳本會產生：

`public/data/lanepilot/lane-guidance.json`

這份檔案只保留導航所需欄位：

```ts
interface LaneGuidanceRecord {
  wayId: number
  direction: 'forward' | 'backward'
  scope: 'intersection_approach' | 'segment_direction' | 'legacy'
  intersectionNodeId?: number
  laneCount?: number
  laneMovements: string[]
}
```

產生器必須：

- 讀取內建的 `annotations.jsonl`。
- 擷取有效的車道設定。
- 正規化標註範圍與路口識別資料。
- 以固定順序輸出，確保相同輸入一定產生相同檔案。
- 遇到可能造成索引鍵含糊的錯誤識別資料時，讓建置失敗並指出來源。
- 讓 `LaneDev` 與 `LaneNav` 產生完全相同的結果。

目前 9.1 MB 的完整標註檔，精簡後約為 102.5 KB；使用 gzip 傳輸時約為 7.5 KB。

開發伺服器與正式版建置之前都會重新產生精簡檔，避免來源標註已變更、執行時資料卻沒有同步更新。

## 執行時索引

系統會在載入道路資料的同時載入精簡車道資料，並建立兩個索引：

```ts
approachByKey: Map<`${wayId}@${nodeId}/${direction}`, LaneGuidanceRecord>
segmentByKey: Map<`${wayId}/${direction}`, LaneGuidanceRecord>
```

建立索引前，標註資料必須套用道路準備流程產生的同一份 `nodeRemap` 與 `wayRemap`。如果原始道路已被 couplet 合併移除，該標註會複製到保留下來的一個或多個道路 ID。若既有 couplet 資訊指出被吸收道路與保留道路的方向相反，則交換 `forward` 與 `backward`。路口進場標註的節點 ID 也會在此階段一併轉換。

只有在道路圖與車道資料索引都符合下列其中一種狀態後，地圖載入才算完成：

- 成功載入；或
- 明確載入失敗，並已啟用 OSM／系統推測的降級流程。

載入期間不開放路線規劃與開始導航控制。因此不會發生導航已經開始、車道資料卻還沒載入完成的情況。

索引只會在建立轉彎步驟或目前道路段改變時查詢。導航動畫的每一幀都不會重新解析 JSON，也不會線性掃描全部標註。

## 路線與 HUD 整合

建立轉彎步驟時，進場道路已經能提供：

- 進場道路 ID。
- 路口節點 ID。
- 正向或反向行駛方向。
- 道路車道數。
- OSM 車道轉向陣列。

車道導航解析器會將上述資料與人工標註索引合併，並把結果存入轉彎步驟：

```ts
interface ResolvedLaneGuidance {
  laneCount: number
  laneMovements?: string[]
  source: 'annotation' | 'annotation+osm' | 'osm' | 'inferred'
}
```

HUD 根據距離選擇資料：

- 距離下一個轉彎超過 250 公尺時，顯示目前道路段的車道資料。
- 距離下一個轉彎小於或等於 250 公尺時，顯示下一個轉彎進場道路解析後的車道資料。

只有在 `source === 'inferred'` 時顯示「車道建議（系統推測）」。人工標註、人工標註搭配 OSM，以及純 OSM 資料都不會被標為系統推測。

## 失敗與例外處理

- 找不到精簡資料檔：只輸出一次明確警告，地圖初始化完成後改用 OSM／系統推測。
- 個別標註無效：產生器指出原始資料識別並讓建置失敗，避免錯誤資料進入發布版本。
- 找不到相符的路口進場標註：依序改用一般路段、舊格式、OSM，最後才推測。
- 車道數與方向陣列長度不一致：逐條車道合併，不因部分資料缺少而放棄整組資料。
- 遇到無法辨識的方向字串：維持未知，不可因此高亮該車道。
- 車道數超過十條：維持現有的預覽截斷行為。

## 測試

### 資料產生器測試

- 能擷取正向與反向車道設定。
- 路口進場標註會保留路口節點。
- 輸出順序固定。
- 拒絕含糊或無效的路口進場識別資料。
- 能從內建標註測試資料產生精簡檔。

### 車道資料解析器測試

- 路口進場標註優先於一般路段標註與 OSM。
- 沒有相符路口標註時，使用一般路段標註。
- 保留對舊格式標註的支援。
- 人工已知值逐車道覆蓋 OSM。
- 人工 `unknown` 逐車道使用 OSM 補值。
- 反向行駛不得誤用正向資料。
- couplet 道路與節點轉換後仍能找到標註，並在需要時正確交換行駛方向。
- 同一條道路的其他路口不得誤用特定進場標註。
- 部分方向陣列仍保留已知資料，不得整組改成系統推測。

### HUD 與模型測試

- 超過 250 公尺時使用目前道路段資料。
- 剛好 250 公尺時切換成下一個轉彎的進場資料。
- 人工標註與 OSM 來源不顯示系統推測提示。
- 幾何 fallback 仍會顯示「車道建議（系統推測）」。

### 整合驗證

- 在 `LaneDev` 與 `LaneNav` 執行車道導航測試。
- 建置兩份專案。
- 確認兩份精簡資料完全相同。
- 模擬經過已有人工標註的路口，確認 HUD 使用人工標註方向。
- 確認車道資料尚未準備完成時，無法開始導航。

## 開發版與發布版同步

程式先在 `LaneDev` 實作，再透過現有同步流程複製到 `LaneNav`。精簡執行時資料與產生腳本都必須納入同步範圍。使用者既有的 lockfile 與原始圖片資料變更不會放進本功能提交。
